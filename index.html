The SafeGDScript language

Familiar syntax.
More ways to express it.

SafeGDScript extends GDScript with reusable behavior and more expressive types. A few small examples show what that looks like in your scripts.

01

Traits

Share state and behavior across scripts. Declare a trait, then bring its members into your script with 'uses Trait'.

uses Damageable

trait Damageable:
    var health: int = 100

    func take_damage(amount: int) -> void:
        health -= amount
02

Nullable types

Use T? for a value that can be null. A null check narrows the type so you can safely work with the value that remains.

func bonus_points(bonus: int?) -> int:
    if bonus == null:
        return 0
    return bonus + 10
03

Structs

Group related variables of different types together under a single name. Construct a value directly and access its fields by name.

struct Item:
    var name: String
    var value: int

func starting_item() -> Item:
    var item := Item("Potion", 25)
    item.value += 5
    return item
04

Compact if var

Bind a non-null value and use it inside the branch in one step. It's only a null check. 0, false, and empty strings still pass.

func score_label(score: int?) -> String:
    if var points := score:
        return str(points) + " points"
    return "No score yet"
05

Union types

Accept a specific set of types with |. Test with is to narrow the value and handle each case with the right operations.

func item_label(item: int | String) -> String:
    if item is int:
        return "Item #" + str(item)
    return item + " (named)"

A few things worth knowing.

Can sandboxed scripts be AOT-compiled?

Yes, if you want. Ahead-of-time compilation can be fully native (2-5x performance for regular GDScript), or sandboxed (costlier, but matching GDScript). Keep the restricted configuration for untrusted mods.

Does it work on every platform?

The runtime and AOT approach span desktop, mobile, web, and console targets, including systems without JIT. Your export needs the matching target toolchain and integration. The separately priced Studio module loads the same artifacts as the BSD extension. Console builds are untested by us; SDK access and console ports are separate.

Why not just embed Lua?

A scripting language alone is not a security boundary. A Lua integration needs carefully restricted host bindings, libraries, and resource limits to handle untrusted code. Godot Sandbox provides a dedicated isolated runtime with a zero-outside-access restriction mode and an explicit game API.

Do I need to upload my game or license my players?

No. Compilation runs locally. Commercial tooling is licensed for development and export. The shipped runtime does not ask players for a license key.

Why obfuscation?

I'm seeing more and more threads about people having their games repackaged and resold, presumably via semi-automated processes using LLMs. I want to make it harder for casual attackers to reverse engineer released games.

What does script obfuscation protect?

Supported scripts ship as stripped machine code rather than tokenized source, making casual recovery much harder. Engine-visible names, some strings, scenes, and assets may remain inspectable. Obfuscation does not make code impossible to reverse engineer. Check your export report for scripts that remain as source.

How does GS+ obfuscation compare with Godot's encryption?

Godot's PCK encryption protects files on disk. The game ships with the key and decrypts scripts when loading them, exposing their source text or tokenized representation in memory for an analyst to recover. Encryption does not turn GDScript into machine code.

Godot Sandbox Plus compiles supported scripts into RISC-V machine code and can execute AOT native machine code. The shipped game never needs to reconstruct those scripts' source or tokens, even at load time. Obfuscation further removes eligible internal names and obscures selected strings, so recovering the implementation requires reverse engineering compiled code. Engine-visible names and some strings can still be inspected.
